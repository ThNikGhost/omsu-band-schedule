# astrobox-plugin — плагин синхронизации для AstroBox

Забирает расписание с сервера и отправляет его на браслет. Плагин **AstroBox v2**:
WebAssembly-компонент на Rust, `wasi_version: 2`, `api_level: 3`, пакет `.abp`.

> Плагины на JavaScript относятся к AstroBox v1 и больше не работают: загрузчик
> принимает только `api_level` 2 или 3. Подробности и подтверждения — в
> [`docs/DECISIONS.md`](../docs/DECISIONS.md).

## Устройство

| Крейт | Что внутри |
|---|---|
| `core/` (`omsu-sync-core`) | настройки, протокол, разбор ответа сервера. **Без зависимости от AstroBox** — собирается под хост и покрыт 38 тестами |
| корневой (`omsu-band-schedule-plugin`) | WIT-биндинги, UI настроек, HTTP, отправка на браслет |

Разделение вынужденное и полезное: биндинги компилируются только под
`wasm32-wasip2`, поэтому всё, что лежит рядом с ними, юнит-тестами не покрыть.

## Сборка

Нужны Rust и Python 3:

```bash
rustup target add wasm32-wasip2
```

```bash
cargo build --release
```

```bash
python3 scripts/build_dist.py --release --package
```

Результат — `dist/Расписание ОмГУ.abp` (около 180 КБ). Имя файла берётся из поля
`name` манифеста, поэтому оно кириллическое: для экосистемы это норма, штатные
плагины называются по-китайски.

Тесты ядра идут под хост, а не под wasm — таргет приходится указывать явно,
потому что `.cargo/config.toml` по умолчанию собирает в wasm:

```bash
cargo test -p omsu-sync-core --target x86_64-unknown-linux-gnu
```

### Если `cargo` блокируется Windows

На машине разработки Smart App Control запрещает запуск `cargo.exe` (ошибка 4551).
Отключать его нельзя — это необратимо. Сборка идёт в WSL2, где политика не
действует; вспомогательные скрипты лежат вне репозитория, а суть такая:

```bash
wsl -d Ubuntu bash -lc "cd /mnt/d/vscode/smart_band_10/astrobox-plugin && CARGO_TARGET_DIR=~/.cargo-target/omsu cargo build --release"
```

`CARGO_TARGET_DIR` выносится в файловую систему Linux: сборка на `/mnt/d` через 9p
заметно медленнее.

## Установка

AstroBox → страница плагинов → «+» в правом верхнем углу → выбрать `.abp`.
После установки AstroBox попросит перезапуск и спросит разрешения.

Запрашиваемые разрешения и зачем они:

| Разрешение | Зачем |
|---|---|
| `network` | HTTP-запрос к серверу расписания |
| `device` | узнать адрес подключённого браслета |
| `interconnect` | отправка сообщений приложению на браслете |
| `register_interconnect_recv` | подписка на ответы браслета; без неё они не доходят |
| `thirdpartyapp` | запустить приложение на браслете перед отправкой |

## Настройки

Заполняются в окне плагина: адрес сервера, токен, номер группы, подгруппа
(пусто = все пары), сколько дней вперёд, package name приложения на браслете.
Здесь мы с девушкой и расходимся — сервер один, подгруппы разные.

**Два способа ввода, и это не избыточность.** Встроенное поле поначалу не принимало
текст вовсе: мы передавали хосту `value`, он считает это управляемым свойством и после
каждого нажатия возвращал поле к последнему отрисованному значению. Теперь передаётся
`defaultValue` — начальный текст без дальнейшего вмешательства. Сверить это было не с
чем: **ни в одном публичном плагине AstroBox нет текстовых полей**. Поэтому рядом с
каждым полем стоит кнопка «Ввести», открывающая `dialog::show-dialog` с
`DialogType::Input` — нативный диалог с системной клавиатурой. Если откажет один путь,
останется второй.

Под каждым полем видно сохранённое значение. Токен показан только длиной: экран
телефона слишком легко попадает в кадр.

Токен уходит **только в заголовке** `Authorization`, никогда в URL — иначе он
осел бы в логах и на прокси.

Настройки лежат в `omsu-band-schedule.config.json` в каталоге плагина: своего
config-API в AstroBox v2 нет, а WASI даёт плагину ровно одну папку на запись.
Сохранение идёт через временный файл и переименование, с откатом на прямую
запись — атомарное переименование поддерживают не все WASI-файловые системы.

## Протокол

Полезная нагрузка — около 4.4 КБ на 14 дней, поэтому **штатный путь — одно сообщение**
`sync_full`. Проверено на живом Band 10: **сообщение в 4288 байт дошло одним кадром**,
нарезка не понадобилась. Верхняя граница не измерена — 4288 это то, что понадобилось. Расписание вкладывается
объектом, а не строкой: escape-последовательности раздули бы каждую кириллическую
букву и примерно удвоили кадр.

Нарезка — запасной путь: `sync_begin` → `sync_part` × N → `sync_end`, кусок 4 КБ,
окно 4 кадра, подтверждение **на каждый кадр**. Отправлять всё подряд из одного
вызова `on_event`, не возвращая управление хосту, нельзя — так забивается очередь
BLE и передача умирает. Это задокументированная ошибка, из-за которой официальный
плагин FetchBridge переписал свой протокол.

## Проверено на живом AstroBox

16.09.2026, Android. Плагин установился, настройки сохранились, синхронизация прошла
насквозь: сервер → телефон → браслет.

- **Формат `event_payload`** для событий ввода разбирается и как строка, и как JSON —
  какой приходит на самом деле, так и не понадобилось выяснять: ввод в итоге идёт через
  нативный диалог.
- **Задержки 2 с** после запуска приложения на браслете хватило.
- **`register_interconnect_recv` оформлялся только в `on_load`** — и если браслет в тот
  момент не был подключён, подписка пропускалась навсегда, а запросы браслета уходили в
  никуда. Исправлено: `sync::ensure_subscribed()` переоформляет подписку при загрузке,
  при действии с устройством и при открытии настроек.

Осталось непроверенным:

- Поведение на iOS: там WASM исполняется интерпретатором, без JIT. Вся проверка шла
  на Android.
- Совместная работа с Mi Fitness на одном телефоне при длительной эксплуатации.
